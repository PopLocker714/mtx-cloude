# oko-cloud — план реализации

Сервис: пользователь подключает свои камеры → облачная запись 7 дней бесплатно → live и архив в ЛК.
Целевой рынок: Украина. Ядро (MediaMTX) уже задеплоено и проверено (этап 0 ✅).

## Ключевое архитектурное решение — мультитенантность

MediaMTX сам не знает про «пользователей» — он про потоки. Чтобы «камера X принадлежит юзеру Y, смотреть может только Y» — ставим **наш backend авторизатором MediaMTX** через его штатный внешний auth-hook (`authHTTPAddress`): на каждый connect/publish/read/playback MediaMTX спрашивает наш API «этому токену можно на этот путь?», API отвечает да/нет. Так на одном MediaMTX получаем полноценную мультитенантность без форка.

```
Камера/бридж ──RTSP──▶ MediaMTX ──auth POST──▶ наш Backend (кто чей, токены)
                          │                          │
   ЛК/приложение ◀─live/архив─┘         Postgres: users, cameras, bridges, sessions
```

## Стек (зафиксирован 2026-07-20)

Монорепо **Bun workspaces + Turborepo**: `apps/api`, `apps/web`, `apps/mobile`, `packages/*` (общие типы, API-клиент, zod-схемы). Общие типы между backend и клиентами через Hono RPC (`hc<AppType>()`) — нет рассинхрона API.

| Компонент | Что делает | Технологии |
|---|---|---|
| **Bridge-агент** | живёт в LAN пользователя, тянет RTSP с камер и пушит в облако исходящим соединением; ONVIF-автообнаружение, pairing по коду, авто-reconnect/update | Bun + ffmpeg (remux `-c copy`), Docker + бинарь; образ для RPi |
| **Backend/API** ✅ построен | пользователи (Better Auth), реестр камер/бриджей, pairing-коды, **auth-hook MediaMTX**, каркас биллинга | Bun + Hono + Postgres (Drizzle) + Better Auth |
| **Web** (маркетинг + ЛК + админка) | публичный сайт (SSR, SEO, EN/UK), личный кабинет, админ-панель | **TanStack Start** (v1.x) + **shadcn/ui** (все компоненты) + Paraglide i18n |
| **Mobile** | live-просмотр, архив, уведомления | **React Native BARE (без Expo)**, RN 0.86, react-navigation 7, react-native-video (HLS) + react-native-webrtc (live) |

**shadcn/ui — берём всё готовое, не пишем руками:** sidebar, breadcrumbs, data-table (TanStack Table), формы (react-hook-form + zod), dropdown, avatar/профиль, dashboard-блоки (`dashboard-01`). И ЛК пользователя, и админка главного админа — на нём. Ставится `shadcn init -t start`.

**Web = две поверхности в одном TanStack Start:**
- **Публичный маркетинг-сайт** — SSR + prerender, для SEO на двух языках.
- **Дашборд (ЛК + админка)** за авторизацией — client-heavy, локаль из куки.

## Подключение сторонних камер — три класса (главный вопрос)

Ключевое: под разные камеры — разный способ завода в наш MediaMTX. Наш bridge — единая точка, внутри — адаптеры.

| Класс камеры | Примеры | Как подключаем | Этап |
|---|---|---|---|
| **RTSP/ONVIF** (инсталляторские) | Hikvision, Dahua, Reolink, Uniview, TP-Link Tapo* (Camera Account), Imou* (RTSP-тумблер) | bridge: ONVIF-discovery → тянет RTSP → пуш в облако. **Основной путь MVP.** | 1 |
| **P2P (proprietary)** | Wyze/TUTK, X5/A9/iLnk, Xiongmai, Tuya, V380/Yoosee | адаптер под стек: определить по broadcast/QR → готовый бридж (docker-wyze-bridge / cam-reverse / neolink / python-dvr / tuya-ipc-terminal) → в наш MediaMTX. **Твоя текущая камера — сюда.** | 3 |

\* Tapo/Imou имеют RTSP, но с оговорками (облачный аккаунт, капризные прошивки) — поддерживаем, но помечаем.
\* Партнёрские прошивки (камера пушит сама, без bridge) — **исключено из плана** (слишком заморочено: договоры с вендорами).

## Языки и SEO (EN + UK)

- **Английский — базовый** (без префикса: `/about`), **украинский — префикс `/uk/about`**. Украинский обязателен — основная аудитория; SEO нужен на обоих.
- i18n — **Paraglide JS** (официальная для TanStack, compile-time, tree-shakeable). Локаль публичных страниц — из URL (не из куки/Accept-Language, иначе Google не проиндексирует украинский).
- **Обязательно:** взаимные `hreflang` (`en`, `uk`, `x-default`) в `<head>` и в sitemap; язык-код **`uk`**, не `ua` (ua невалиден). Prerender маркетинг-страниц на обоих языках.

## Масштабируется ли MediaMTX? (да, но со схемой)

Коротко: **ingest дёшев (тысячи камер на инстанс, упор в сеть), но раздача — узкое место, и первым ляжет WebRTC (только 100–200 зрителей на инстанс).** Нативной кластеризации у MediaMTX нет — масштабируют «много stateless-инстансов + внешний оркестратор».

Ключевые лимиты одного инстанса (бенчмарки maintainer + практика): ~2800 RTSP-потоков ingest (упор в NIC), 500+ RTSP/HLS зрителей, **но 100–200 WebRTC** и **запись фризит при >550 потоках**. Вывод: **разделять роли — ingest / delivery / record — в отдельные пулы** с самого начала архитектуры.

Дорожная карта роста:
- **10 камер** — один инстанс (уже есть), запись локально + rclone в S3/MinIO, retention — lifecycle бакета.
- **100 камер** — отдельные record-инстансы (≤100 записей/контейнер), раздача RTSP/HLS за nginx/HAProxy, список камер в БД (источник истины вне MediaMTX).
- **1000 камер** — k8s, ingest/delivery/record split, шардинг камер + Redis service discovery, WebRTC — выделенный слой с session-affinity + флот coturn (или SFU).
- **10000+** — свой control-plane дорог; смотреть **Kerberos Factory** (k8s-оркестрация агентов) или **managed Kinesis Video Streams**; WebRTC-раздачу — на **SFU (LiveKit/Janus/Ant Media)**.

Принцип «чтобы ничего не легло»: ingest/delivery/record — раздельно; истина о камерах — вне MediaMTX; retention — на бакете; **под WebRTC закладывать отдельную инфраструктуру заранее** (это первый узел у потолка). Для нас: HLS — основной массовый способ раздачи (дёшево, CDN), WebRTC — только где нужна секундная задержка.

## Безопасность (аудит 2026-07-20)

Проведён security-аудит. **Исправлено и проверено вживую:** секрет Better Auth fail-closed (падает без длинного секрета), pairing-код с TTL 15 мин + single-use, IDOR по bridgeId закрыт, `isPrivateIp` больше не пускает публичные 172.x, CORS + кросс-сабдоменная кука (`SameSite=None; Secure`, domain `.tunnel.poploker.ru`), rate-limit Better Auth, валидация входных данных, обработчик ошибок без утечки стека, Docker: frozen-lockfile + non-root + .dockerignore.

**Осталось (следующими итерациями):** email-верификация (нужен SMTP-транспорт), ротация/отзыв publishToken, GC истёкших view-токенов, аудит листинга god-view в админке, не логировать view-токены в query на Traefik.

Хорошее, что НЕ ломать: токены CSPRNG, роль admin не эскалируется регистрацией, нет SQL-инъекций, изоляция тенантов в auth-hook, backend/postgres не публикуются наружу.

## Этапы

### Этап 1 — MVP «одна камера, один юзер» (ядро сервиса)
- Backend: схема БД (users, cameras, bridges, pairing_codes, view_audit), auth magic-link, **auth-hook для MediaMTX**.
- Bridge v0: Docker-контейнер, вводишь pairing-код + RTSP-URL камеры вручную → пуш в облако. (Автообнаружение — в этапе 2.)
- ЛК v0: логин, добавить камеру (pairing-код + путь), список, live-плеер WebRTC, таймлайн архива, скачать клип.
- Инфра: TLS + домен через Traefik, боевые секреты.
- **Готово, когда:** незнакомый юзер регистрируется, заводит свою RTSP-камеру через bridge, видит live и 7-дневный архив только своей камеры.

### Этап 2 — Web (маркетинг + ЛК + админка) + онбординг
- Монорепо (Bun workspaces + Turborepo), общий Hono RPC-клиент.
- **TanStack Start + shadcn/ui**: публичный сайт (SSR, EN/UK, SEO) + ЛК (список камер, live-плеер, таймлайн архива, скачивание, шаринг) + админ-панель (все камеры, consent-gate, audit-log).
- Better Auth кросс-сабдомен между `app.` и `api.` (уже сконфигурировано).
- Bridge v1: ONVIF-автообнаружение камер, ввод только логина/пароля камеры, авто-reconnect/update.
- Уведомления о движении (ONVIF events).

### Этап 3 — P2P-камеры (включая твою)
- Определитель стека (broadcast-снифер + разбор QR).
- Адаптеры-обёртки: интеграция готовых бриджей под стеки в наш bridge.
- **Тут подключаем твою текущую камеру** — как первый тест-кейс P2P-ветки.

### Решения (2026-07-20)
- **Домен** `tunnel.poploker.ru` — временный, на SEO/бренд пока не закладываемся.
- **Email** — **Resend** (верификация, уведомления).
- **MVP без оплаты и тарифов** — «подключил и всё». Но код проектируем так, чтобы легко добавить платные плюшки (глубже архив, 24/7, больше камер, аналитика): ретенция как параметр на камеру/план, а не хардкод 168h.
- **Плеер**: **HLS по умолчанию** (массовый просмотр, дёшево), **WebRTC только для кнопки «live сейчас»** (низкая задержка).

### Этап 4 — Монетизация и рост
- Платные тиры (30 дней, 24/7, больше камер), биллинг, аналитика движения, партнёрская программа для инсталляторов, мобильное приложение.
- (Партнёрские прошивки вендоров — НЕ делаем, слишком сложно организационно.)
